# Future Steps

This document tracks concrete, non-trivial extensions this project's own docstrings and design decisions have already flagged as deliberately out of scope for the current build — organized by what unlocks them. Nothing here is a mystery gap; every item below is cross-referenced to the exact place in the codebase that documents why it wasn't done now.

## 1. Actually running the CARLA-attached path

`src/simulation/carla_bridge.py`'s `CarlaTickSource` is written correctly against the documented CARLA 0.9.15 Python API, but has never been executed — this development machine cannot run it (see `docs/SETUP.md`'s "Optional: CARLA closed-loop simulation" and `docs/modules/simulation/carla_bridge.md`). To close this gap for real:

1. **Get access to a discrete-GPU machine.** CARLA's server needs one even in headless/off-screen mode (`-RenderOffScreen`); an Intel iGPU (this machine's actual hardware) is not sufficient. A cloud GPU instance (AWS `g4dn`, a university lab machine, or a personal desktop with an NVIDIA card) all work — `configs/carla_config.json`'s `host`/`port` fields exist specifically so the CARLA *server* can run on a different machine than wherever `closed_loop_runner.py` is invoked from.
2. **Set up the separate Python 3.8-3.10 venv** described in `docs/SETUP.md` (`requirements-carla.txt` pins `carla==0.9.15`; that venv also needs `requirements.txt`'s other dependencies, since `closed_loop_runner.py` calls into `feature_extraction.py`/`odd_classifier.py`/`rss_safety.py` regardless of which `TickSource` is active).
3. **Run it and diff against the fallback.** The most useful first real-hardware task isn't a new feature — it's running `python -m src.simulation.closed_loop_runner --num_ticks 200` with `configs/carla_config.json`'s `use_carla: true` and comparing the resulting mode/RSS-distance/stability-margin distributions against an equivalent `--force_fallback` run on the same machine, to sanity-check that `CarlaTickSource`'s real kinematics produce a qualitatively similar decision pattern to the local kinematic model's synthetic ones (they're not expected to match exactly — the fallback's straight-line, no-steering assumption is a real simplification — but wildly different distributions would flag a bug in `carla_bridge.py` worth investigating).
4. **A real per-axle slip-angle model.** `closed_loop_runner.py` currently approximates both `alpha_f` and `alpha_r` as the vehicle's overall sideslip angle (documented in `closed_loop_runner.md`'s "Key Design Decisions"), since neither tick source exposes steering-angle/yaw-geometry detail. With CARLA's `vehicle.get_control().steer` and known wheelbase geometry (`config.vehicle_blueprint`'s physics control already exposes `wheels[i].position`), a real per-axle slip angle is computable and would make `sideslip_dynamics()`'s inputs more faithful.
5. **A scripted (non-autopilot) adversarial lead vehicle.** `CarlaTickSource` currently spawns the lead vehicle on CARLA's built-in autopilot (`local_kinematic_sim.md` documents why the fallback can't do the equivalent — no real lead-vehicle measurement exists in IDD-Lite at all). A scripted lead vehicle that deliberately brakes hard partway through a run would let the RSS distance formula's braking-phase term actually get exercised under a real hard-braking scenario, rather than autopilot's typically-smooth car-following behavior.
6. **Multi-vehicle / multi-town scenarios.** Right now `CarlaTickSource` spawns exactly one ego vehicle and one lead vehicle in `config.town`'s first spawn point. A real stress test would place several background vehicles (CARLA's traffic manager supports this natively) and run across more than one town to see whether Stage 5's ODD-region classification and Stage 7's mode assignment stay sensible across denser traffic.
7. **RL-tuned physics profiles.** `carla_config.py`'s per-mode `PhysicsProfile`/`WeatherProfile` values (target speed, tire friction, weather intensity) are this project's own hand-picked defaults (documented in `docs/FORMULA_PROVENANCE.md` as not paper-derived), not calibrated against any objective. A natural next step: treat them as a small parameter space and search it (even simple grid search, or a lightweight RL policy) against a safety/comfort objective built from `rss_safety.py`'s own margin outputs.

## 2. True live dashboard polling

`dashboard/app.js`'s `initCarlaReplay()` animates a **finished, bounded** run (`dashboard/carla_live.js`, written once at the end of `run_closed_loop_simulation()`) via client-side `setInterval` — deliberately, to stay consistent with this project's `file://`-only dashboard philosophy (no local server anywhere else in the project; see `docs/modules/simulation/closed_loop_runner.md`'s "Key Design Decisions"). A genuinely **live** view — watching ticks arrive while a simulation is still running, rather than replaying a completed one — would need:

1. `closed_loop_runner.py` writing a real `dashboard/carla_live.json` (plain JSON, not a `const` JS global) incrementally, every few ticks, instead of once at the end.
2. A tiny local dev server (Python's stdlib `http.server.ThreadingHTTPServer` is sufficient — no new dependency) serving the `dashboard/` directory, since `fetch()` of local files is blocked under `file://` but works fine over `http://localhost`.
3. `app.js` polling that endpoint with `setInterval(() => fetch('carla_live.json')..., 2000)`, guarded (`location.protocol.startsWith('http')`) so the existing `file://`-based static mode keeps working unchanged when no server is running.

This was explicitly considered and deferred in favor of the replay-array approach during Stage 8's design — see `docs/modules/simulation/closed_loop_runner.md` for the reasoning (a finished run doesn't need live infrastructure; the added server-lifecycle complexity wasn't justified for a bounded, already-complete dataset).

## 3. A real validation-split image loader

`local_kinematic_sim.py`'s fallback tick source cycles through `data_pipeline.load_and_clean_dataset(DATA_DIR)`'s **train**-split images (there is no `leftImg8bit/val/` loader anywhere in this codebase, even though that directory exists on disk — confirmed directly during Stage 8's design). This matches `perception_monitor.py`'s existing precedent of reusing train-split images for non-training purposes, but a cleaner long-term setup would add a `load_and_clean_dataset(dataset_dir, split="val")` parameter (or a sibling function) so simulation/monitoring code paths don't implicitly reuse training data.

## 4. Other proposal-adjacent stretch items (pre-existing, not new)

These were already flagged as scope decisions before Stage 8 existed (see the top-level README's "Known scope limitations" and `docs/FORMULA_PROVENANCE.md`'s "Adapted, not literal" section) — listed here for completeness since they're the same kind of "documented gap with a clear next step" as the CARLA items above:

- **KITTI cross-dataset validation.** The proposal lists KITTI alongside IDD-Lite; it was skipped because it doesn't test this project's India-specific novelty claim. A future pass could run the trained SegNet/YOLO/ODD-classifier pipeline against KITTI images (with KITTI's own class scheme separately verified the same way IDD-Lite's was — see `docs/DATASET_NOTES.md`'s closing "Lessons" section) to check whether the India-specific feature calibrations (traffic density thresholds, fuzzy wetness breakpoints) generalize or need per-dataset recalibration.
- **True-video Stage 6 monitoring.** `perception_monitor.py` currently uses a perturbation-sequence proxy (repeated perturbed versions of one static image) instead of real consecutive video frames, since IDD-Lite has none. A dashcam-video dataset (or CARLA's own camera stream, now that Stage 8 exists — `CarlaTickSource.tick()` already produces a real frame sequence) would let `run_perception_monitor()` track genuine frame-to-frame IoU/confidence consistency instead of the perturbation proxy.
- **Calibrating `detect_pothole_candidates()`.** This heuristic (dark, compact, irregular blobs in the drivable-area region) has no ground-truth pothole labels to validate against anywhere in IDD-Lite (see `docs/DATASET_NOTES.md`). A small manually-labeled sample (even a few hundred frames) would let this move from "uncalibrated heuristic" to an actual precision/recall-evaluated detector.
- **A Kriging surrogate model for `risk_estimation.py`.** Jiang et al. 2024's original Subset Simulation framework uses a Kriging surrogate and Metropolis-Hastings resampling against a live driving simulator to generate new candidate points; `risk_estimation.py` instead applies the same nested-threshold decomposition structure to a static population (documented in `docs/FORMULA_PROVENANCE.md`'s "Adapted, not literal" section) because there was no simulator. Now that Stage 8 provides one (real or fallback), a real Kriging-based resampling loop against `closed_loop_runner.py`'s tick stream is a natural, literal implementation of the paper's actual method rather than the current static-population adaptation.
- **AOS/APH real orientation output.** `detection_benchmark.py` implements Nawaz et al. 2023's orientation-similarity formulas exactly but has no orientation ground truth to apply them to (this project's 2D bounding boxes carry no heading). CARLA actors *do* expose a real heading (`transform.rotation.yaw`) — a future pass could project ego/lead-vehicle heading into 2D detections during a Stage 8 run and finally exercise AOS/APH against real, non-synthetic data.
